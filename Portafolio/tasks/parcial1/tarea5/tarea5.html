🎯 Objetivo and Contexto

Objetivo General: Implementar una estrategia completa de respaldos logicos para sistemas gestores de bases de datos heterogeneos (MariaDB y PostgreSQL) en un entorno Linux (CentOS 8), utilizando las herramientas nativas de cada motor, gestionando correctamente permisos y propietarios de archivos, identificando errores reales en el proceso y documentando su resolucion.

Contexto: La administracion de bases de datos requiere una estrategia robusta de respaldos. Esta tarea simula un escenario real donde un administrador debe: (1) crear estructura de directorios, (2) generar respaldos completos, (3) gestionar permisos y propiedad, (4) identificar y corregir errores tipicos como typos en comandos, permisos insuficientes, y rutas incorrectas, (5) validar la estructura con herramientas del sistema.

Alcance: Se cubren respaldos logicos (exportacion SQL) para MariaDB 10.x y PostgreSQL 12+, gestion de usuarios, permisos en Linux (chmod, chown), y validacion con tree. Se EXCLUYEN respaldos fisicos (binary logs, WAL) y replicacion.

💡 Conceptos Clave

Respaldo Logico (Logical Backup)

Exportacion de la estructura DDL (CREATE TABLE, indices) e inserciones DML (INSERT) de una BD a un archivo SQL. Ventajas: portable, legible, puedo restaurar parcialmente. Desventajas: mas lento que fisico para DBs grandes.

mysqldump - Herramienta de Exportacion

Cliente MySQL/MariaDB que genera dumps logicos. Puede ser lento en datos > 1GB por lock de lectura. Sintaxis: mysqldump -u usuario -p BD_name > respaldo.sql

pg_dumpall - Cluster PostgreSQL

Exporta TODAS las BDs del cluster + usuarios + configuracion. Esencial para migraciones. No requiere lock, usa snapshots. Genera archivo SQL restaurable con psql.

Permisos Linux: chmod and chown

chmod: Modifica rwx (lectura/escritura/ejecucion). Formato: chmod 600 = solo propietario lee/escribe. chown: Cambia propietario:grupo. Critico: archivos de BD deben ser propiedad del usuario que restaura.

Estructura de Directorios Jerarquica

Organizacion: Backups/ - [MariaDB/, PostgreSQL/, Historico/]. Permite: facil localizacion, backup selectivo por motor, rotacion independiente. Herramienta tree visualiza jerarquia.

Validacion de Integridad

Verificar: (1) Archivo SQL sintacticamente correcto, (2) Contiene CREATE TABLE/INDEX, (3) Can restore sin errores, (4) Datos post-restauracion = pre-backup. Usar SELECT COUNT() para auditar.

🔧 Implementacion - 5 Pasos

Paso 1: Crear Estructura Jerarquica

sudo mkdir -p /Backups/MariaDB /Backups/PostgreSQL /Backups/Historico
sudo chmod 700 /Backups
ls -l /Backups

Paso 2: Respaldo Logico de MariaDB

sudo mysqldump -u root -p --all-databases > /Backups/MariaDB/dump_mariadb.sql
sudo chown root:root /Backups/MariaDB/dump_mariadb.sql
sudo chmod 600 /Backups/MariaDB/dump_mariadb.sql
wc -l /Backups/MariaDB/dump_mariadb.sql  # Verificar tamano

Paso 3: Exportacion de Cluster PostgreSQL

sudo -u postgres pg_dumpall > /Backups/PostgreSQL/dump_postgresql.sql
sudo chown postgres:postgres /Backups/PostgreSQL/dump_postgresql.sql
sudo chmod 600 /Backups/PostgreSQL/dump_postgresql.sql

Paso 4: Gestion de Permisos - Identificar Errores

# INCORRECTO: permisos demasiado abiertos
sudo chmod 644 /Backups/MariaDB/dump_mariadb.sql  # Cualquiera puede leer

# CORRECTO: solo propietario
sudo chmod 600 /Backups/MariaDB/dump_mariadb.sql

# Verificar
ls -l /Backups/MariaDB/

Paso 5: Validacion con tree

sudo yum install -y tree
tree /Backups/
# Salida esperada:
# /Backups/
# ├── MariaDB
# │   └── dump_mariadb.sql
# ├── PostgreSQL
# │   └── dump_postgresql.sql
# └── Historico

✅ Validacion de Respaldos

Paso 1: Estructura de Directorios - Crear jerarquia /Backups con subdirectorios MariaDB, PostgreSQL e Historico para organizar respaldos sistematicamente.

Paso 2: Permisos y Propietarios - Aplicar chmod 600 en archivos de respaldo con chown correcto (root:root para MariaDB, postgres:postgres para PostgreSQL) para seguridad.

Paso 3: Generacion de Respaldos - Usar mysqldump para MariaDB y pg_dumpall para PostgreSQL. Resultado: archivos dump_mariadb.sql y dump_postgresql.sql con tamanios correctos y checksums validados.

❓ Preguntas Frecuentes

¿Respaldo logico vs fisico? ¿Cual usar?

Logico: SQL, portable, legible, restauracion selectiva. MAS LENTO. Ideal: cambios frecuentes, migraciones.

Fisico: Copia binaria, RAPIDO, completo. Pero: puede ser incompatible entre versiones. Ideal: BD grandes, RPO bajo.

¿Por que mysqldump es lento?

Porque bloquea TODAS las lecturas durante el dump (LOCK READ LOCK). Opciones: --single-transaction (InnoDB), --lock-tables=false (pero riesgo inconsistencia), usar read replica.

¿Que errores tipicos al hacer respaldos?

1) Typo: "mysqldum" en lugar de "mysqldump". 2) Permisos: -rw-r--r-- permite que otros lean datos sensibles. 3) Rutas: /var/lib/postgresql/ vs /home/. 4) Espacio en disco: dump llena /tmp. 5) Caracteres especiales en password (-p'pass')

¿Como restaurar un dump?

MariaDB: mysql -u root -p < dump.sql | Usa transacciones de defecto

PostgreSQL: psql -U postgres < dump.sql | Restaura todos los usuarios/bases

¿Validar que respaldo es integro?

1) Grep "CREATE TABLE": grep -c "CREATE TABLE" dump.sql | Debe ser > 0

2) Restaurar en BD test: mysql -u test < dump.sql 2>&1 | grep ERROR

3) Comparar rowcounts: SELECT COUNT(*) FROM tabla antes y despues

¿Automatizar respaldos diarios?

Usar cron: 0 2 * * * /usr/local/bin/backup.sh (todos los dias a las 2 AM). Script: fecha=$(date +%Y%m%d); mysqldump -u root -p > /Backups/MariaDB/dump_${fecha}.sql

¿Comprimir respaldos para ahorrar espacio?

mysqldump ... | gzip > dump.sql.gz | Reduce 80-90%. Restaurar: gunzip < dump.sql.gz | mysql -u root -p

📋 Conclusiones

🎓 Aprendizajes

Los respaldos son arte + ciencia. No solo ejecutar comando, sino entender permisos, integridad, y validacion. MariaDB y PostgreSQL suelen requerir enfoques distintos. Administracion real = prevension de desastres.

⚡ Desafios

Respaldos grandes lentos. Espacio en disco limitado. Restauracion puede fallar si BD destino tiene datos. Permisos confusos entre usuarios postgres/mysql/root.

🚀 Mejoras

Aprender respaldos fisicos (xtrabackup). Replicacion en tiempo real. Automatizacion con AWK/Bash. Monitoreo de backups con Nagios/Prometheus.

Q1: "¿Por que usar respaldos logicos si son lento?"
R: Porque son portables, legibles, permiten restauracion selectiva, y el overhead es aceptable si se usa --single-transaction. Para prod seria respaldos fisicos + replicacion.
Q2: "¿Que hubiera pasado si chmod era 644 en lugar de 600?"
R: Cualquier usuario del sistema podria leer los dumps (incluyendo datos sensibles). Violacion de seguridad. Por eso chmod 600 - solo propietario.
