🎯 Objetivo

Aprender a descargar, validar e importar archivos SQL desde fuentes remotas (GitHub, repositorios públicos, dumps de producción). Incluye validación de integridad, manejo de errores, resolución de conflictos de importación, y verificación post-importación de datos.

💡 Conceptos Clave

Descarga Remota (wget/curl)

Herramientas CLI para descargar archivos desde URLs. wget: simple y directo. curl: versátil con opciones avanzadas (headers, autenticación, resumir). Ambas esenciales en scripting.

GNU wget ↗

Validación de Integridad

Verificar que archivo descargado no esté corrupto: checksums SHA256, MD5, o tamaño de archivo. Previene importar datos corruptos. Ideal con scripts.

SHA-2 Cryptography ↗

Transacciones SQL

BEGIN, COMMIT, ROLLBACK. Si importación falla, revierte cambios. Crítico para no dejar BD en estado inconsistente. SAVEPOINT para rollback parcial.

Database Transactions ↗

Foreign Key Constraints

Restricciones que validan relaciones entre tablas. Durante importación pueden causar errores si datos están desordenados. Soluciones: deshabilitar FK, importar en orden, usar ON DELETE CASCADE.

Foreign Key ↗

Compresión (gzip)

Archivos SQL frecuentemente comprimidos (.sql.gz). Reduce tamaño 80-90%. Descomprimir: gunzip archivo.sql.gz o zcat en pipe. Importante para grandes dumps.

GNU gzip ↗

Backup y Recuperación

Hacer BACKUP antes de importar. mysqldump o pg_dump generan archivos SQL. RESTORE: mysql < backup.sql o psql < backup.sql. Estrategia crítica para producción.

🔧 Pasos de Implementación

Paso 1: Hacer Backup de BD Actual

# MariaDB/MySQL backup
mysqldump -u root -p mibd > backup_preimportacion.sql

# PostgreSQL backup
pg_dump -U postgres mibd > backup_preimportacion.sql

# Comprimir backup
gzip backup_preimportacion.sql

Paso 2: Descargar Archivo SQL Remoto

# Con wget
wget https://github.com/usuario/repo/raw/main/database.sql

# Con curl
curl -O https://ejemplo.com/datos_publicos.sql.gz

# Descomprimir si es necesario
gunzip datos_publicos.sql.gz

Paso 3: Validar Integridad

# Verificar tamaño
ls -lh database.sql

# Validar checksum SHA256
sha256sum database.sql
# Comparar con valor publicado en sitio

# Inspeccionar primeras líneas (sin abrir 1GB archivo)
head -20 database.sql
# Debe tener "CREATE DATABASE", "CREATE TABLE", etc.

# Validar sintaxis SQL sin importar
# MariaDB/MySQL
mysql --no-data -u root -p < database.sql

# PostgreSQL
psql -U postgres --dry-run < database.sql 2>&1 | head -50

Paso 4: Importar con Transacción y Manejo de Errores

# MariaDB - Importación segura
START TRANSACTION;

source /ruta/al/database.sql;

-- Si todo OK
COMMIT;

-- Si ERROR ROLLBACK automático
ROLLBACK;

# PostgreSQL - con script
#!/bin/bash
psql -U postgres mibd << EOF
BEGIN;

\i database.sql

-- Validar conteo de registros
-- SELECT COUNT(*) FROM tabla;

COMMIT;
EOF

Paso 5: Resolver Errores Comunes

-- PROBLEMA 1: Foreign Key violation
-- SOLUCION: Deshabilitar validación durante importación
SET FOREIGN_KEY_CHECKS = 0;
source database.sql;
SET FOREIGN_KEY_CHECKS = 1;

-- PROBLEMA 2: Duplicado de claves primarias
-- SOLUCION: Usar INSERT IGNORE o ON DUPLICATE KEY UPDATE
INSERT IGNORE INTO tabla VALUES (...);
-- O
INSERT INTO tabla VALUES (...) ON DUPLICATE KEY UPDATE col = VALUES(col);

-- PROBLEMA 3: Charset incompatible (latin1 vs utf8)
-- SOLUCION: Convertir archivo antes
iconv -f iso-8859-1 -t utf-8 database.sql > database_utf8.sql

-- PROBLEMA 4: Tipos de datos incompatibles (MySQL vs PostgreSQL)
-- SOLUCION: Editar archivo o usar herramientas de migración
-- MySQL: TINYINT → PostgreSQL: SMALLINT
-- Buscar y reemplazar en archivo si es necesario

Paso 6: Validación Post-Importación

# Verificar integridad de datos
SELECT COUNT(*) FROM usuarios; -- Debe coincidir con origen
SELECT COUNT(*) FROM pedidos;
SELECT COUNT(*) FROM detalles_pedido;

# Validar relaciones
SELECT COUNT(*) FROM pedidos WHERE usuario_id NOT IN (SELECT id FROM usuarios);
-- Si retorna > 0, hay datos huérfanos

# Verificar columnas específicas
SELECT * FROM usuarios WHERE email IS NULL OR email = '';
-- Si hay muchos, problema de integridad

# Hacer backup de BD importada
mysqldump -u root -p mibd > backup_postimportacion.sql

❓ FAQ sobre Importación

¿Cómo detectar si archivo SQL está corrupto?

Métodos: 1) Validar checksum SHA256 2) Verificar tamaño esperado vs. actual 3) Contar líneas CREATE TABLE 4) Intentar validación de sintaxis sin importar (--dry-run) 5) Abrir primeras/últimas líneas

Herramienta: file database.sql muestra tipo. Si dice "data" en lugar de "ASCII text", probablemente corrupto.

¿Qué hacer si importación falla por Foreign Key?

Opción 1: Deshabilitar FK: SET FOREIGN_KEY_CHECKS = 0; antes, activar después.

Opción 2: Reordenar instrucciones en archivo SQL: tablas padres primero, luego referencias.

Opción 3: Usar herramienta de migración (MySQL Workbench, pgAdmin) que ordena automáticamente.

¿Cómo verificar integridad de datos después de importar?

Pasos: 1) Contar registros vs. original 2) Verificar no hay NULLs inesperados 3) Validar foreign keys (consulta huérfanos) 4) Spot-check algunos registros aleatorios 5) Comparar checksums de datos calculados

(Si original: 1000 usuarios, 5000 pedidos → Verificar que importado también tenga estos números)

¿Verdadero o falso: Importar .sql.gz requiere descomprimir siempre?

Falso. Muchas tools aceptan entrada comprimida directamente: mysql < datos.sql.gz o con pipe: gunzip < datos.sql.gz | mysql

Ahorra espacio si archivo es 2GB (descomprimido sería 20GB).

¿Diferencias al migrar MySQL → PostgreSQL?

Problemas: Tipos de datos distintos (TINYINT, AUTO_INCREMENT), sintaxis de constraints, funciones diferentes (DATE_FORMAT vs TO_CHAR), character sets.

Herramientas: pgloader, mysqldump a PostgreSQL, scripts de conversión personalizadas. No es "copy-paste".

¿Cómo asegurar que importación anterior no quedó a medias?

Usar transacciones: BEGIN; ... COMMIT; garantiza que si falló, todo se revierte inmediatamente (sin confirmación).

Sin transacción, pueden insertar 50,000 registros antes de fallar, dejando BD inconsistente.

¿Estrategia recomendada para importar 10GB en producción?

Plan: 1) Backup completo actual 2) Importar en servidor replica/dev primero 3) Validar 4) Usar replicación para sync 5) Switchover con downtime mínimo. 6) Monitorear queries lentas post-import

No hacer: Importar directo en producción sin testing.

📋 Conclusiones

🎓 Aprendizajes

Importación no es solo "ejecutar SQL". Requiere validación, transacciones, manejo de errores y verificación post-importación. Checksum y backup son fundamentales. Scripts automáticos son esenciales para reproducibilidad.

⚡ Desafíos

Archivos SQL gigantes lentos. Errores de Foreign Key frustrantes. Debugging de integridad de datos complicado. Migraciones entre DBMSs (MySQL ↔ PostgreSQL) requieren conversión.

🚀 Mejoras

Aprender herramientas de migración (DMS de AWS, pgloader). Automatizar con Python/Bash scripts. Implementar validación continua. Explorar replicación binaria para BD grandes.

Q1: "¿Por qué validar checksum si puedo solo abrir el archivo?"
R: Porque en tránsito puede corromperse (network error, download parcial). Checksum detecta inmediatamente sin abrir 5GB archivo.
Q2: "¿Qué pasa si transacción falla a mitad de importación?"
R: ROLLBACK automático revierte todo. Sin transacción, quedaría con registros parciales (inconsistencia). Transacción = seguridad.
