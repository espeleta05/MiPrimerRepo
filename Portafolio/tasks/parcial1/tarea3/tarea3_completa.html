🎯 Objetivo y Contexto

Objetivo General: Instalar, configurar y administrar PostgreSQL en máquina virtual CentOS: (1) descargar e instalar PostgreSQL 12+ desde repositorios oficiales, (2) inicializar cluster de datos, (3) crear usuarios/roles con permisos específicos, (4) configurar conexiones remotas (pg_hba.conf, postgresql.conf), (5) diseñar esquema con DDL avanzado (referencias, constraints, índices), (6) ejecutar DML y queries complejas (Window Functions, CTEs), (7) explorar características únicas de PostgreSQL (herencia de tablas, tipos JSON, extensiones).

Contexto: PostgreSQL es DBMS relacional open-source de nivel empresarial (usado por Spotify, Uber, Reddit). Diferencias vs MySQL: tipo datos más ricos (JSON, ARRAY, RANGE), funciones window avanzadas, extensiones (PostGIS geoespacial), MVCC para concurrencia. Destreza en PostgreSQL es diferenciador importante en mercado laboral DevOps/Data Engineering.

Alcance: Cobertura: instalación en CentOS 8, rol Linux de usuario 'postgres', cliente psql, DDL/DML básico+avanzado, configuración usuario/permisos, consultas con agregaciones y window functions, manejo de JSON. EXCLUIDOS: replicación streaming, sharding, análisis de performance extrema, extensiones especializadas (PostGIS, HyperLogLog).

💡 Conceptos Clave Profundizados

PostgreSQL: Características y Arquitectura

DBMS relacional open-source (Licencia PostgreSQL, similar BSD). Versiones: 12 (legacy), 13, 14, 15 (actuales). Arquitectura: Process-per-connection (vs thread-pool de MySQL). Ventajas: ACID completo, tipos datos ricos, confiabilidad (crash recovery), JSON nativo (desde 9.2). Componentes: postgres (servidor principal), postmaster (gestor conexiones), WAL (Write-Ahead Log) para durabilidad.
PostgreSQL Official Docs ↗

Instalación en Linux (CentOS/RHEL)

Proceso: (1) Actualizar repos: dnf update. (2) Instalar PostgreSQL desde oficial repo postgresql.org (vs. CentOS repo desactualizado). (3) Comando: sudo dnf install postgresql12-server. (4) Init cluster: /usr/pgsql-12/bin/postgresql-12-setup initdb. (5) Iniciar: systemctl start postgresql-12. (6) Auto-start: systemctl enable postgresql-12. (7) Verificar: psql -U postgres -c "SELECT version();". Usuario 'postgres' creado automáticamente (admin DBMS).
PostgreSQL on RHEL/CentOS ↗

Roles, Usuarios y Permisos

PostgreSQL usa "roles" (concepto unificado). Tipo: LOGIN role (usuario que se conecta), GROUP role (permisos reutilizables). Creación: CREATE ROLE nuevo_usuario WITH LOGIN PASSWORD 'pass'. Permisos: GRANT SELECT ON tabla TO role. Niveles: SUPERUSER (acceso total), regular USER (limitado), READ-ONLY user (solo SELECT). Parámetro pg_hba.conf controla AUTENTICACIÓN por método (trust, md5, scram-sha-256, ldap). Diferencia MySQL: PostgreSQL no distingue usuario@host, solo usuario + método autenticación.
PostgreSQL User Management ↗

Vistas (Views) y Vistas Materializadas

Vista: Query almacenada que se ejecuta cada vez que se consulta (siempre datos frescos, pero lento si query compleja). Uso: simplificar queries complejas, encapsular lógica, seguridad (exposer solo columnas necesarias). CREATE VIEW v_pedidos_hoy AS SELECT... Vista Materializada: Resultado query precalculado y almacenado físicamente. Rápido en lectura pero datos pueden estar "stale". Requiere refresco manual: REFRESH MATERIALIZED VIEW v_nombre. Uso: reportes complejos actualizados cada noche, data warehouse.
PostgreSQL Views ↗

Window Functions

Función que accede renglon ACTUAL + renglos adyacentes (diferencia de GROUP BY que collapsa filas). Sintaxis: funcion() OVER (PARTITION BY col ORDER BY col2). Ejemplos: ROW_NUMBER() (1, 2, 3...), RANK() (1, 2, 2, 4...), LAG(col, 1) (valor fila anterior), SUM(...) OVER (... ROWS BETWEEN 5 PRECEDING AND CURRENT ROW) (promedio móvil). Uso: cálculos complejos por grupo manteniendo contexto fila original. NO disponible en MySQL hasta versión 8.0.
PostgreSQL Window Functions ↗

Client psql - Herramienta Interactiva

Cliente oficial PostgreSQL en línea de comandos. Comandos: \du (listar roles), \dt (listar tablas), \d nombre_tabla (estructura), \l (listar bases), \i archivo.sql (ejecutar script), \q (quit). Meta-comandos ampliables: \x (JSON formateado), \timing (medir query tiempo), \explain (plan ejecución). Autenticación: psql -U usuario -d base_datos -h localhost -p 5432. Diferencia mysql: psql es más poderoso (meta-comandos útiles para DBA).
psql Reference ↗

📸 Evidencia de Implementación - 6 Pasos Progresivos

Paso 1: Instalación y Verificación de PostgreSQL

Descarga e instalación de PostgreSQL 12 desde repositorio oficial:

#!/bin/bash
# En máquina virtual CentOS 8

# Actualizar sistema
sudo dnf update -y

# Instalar desde repositorio oficial PostgreSQL
sudo dnf install -y https://download.postgresql.org/pub/repos/yum/reporpms/EL-8-x86_64/pgdg-redhat-repo-latest.noarch.rpm
sudo dnf module disable postgresql -y
sudo dnf install -y postgresql12-server postgresql12-contrib

# Inicializar cluster de datos
sudo /usr/pgsql-12/bin/postgresql-12-setup initdb

# Iniciar servicio
sudo systemctl start postgresql-12
sudo systemctl enable postgresql-12  # Auto-start en boot

# Verificar estado y versión
systemctl status postgresql-12
psql --version
# psql (PostgreSQL) 12.18

# Conectar con usuario postgres (admin)
sudo -u postgres psql -c "SELECT version();"
# PostgreSQL 12.18 on x86_64-pc-linux-gnu, compiled by gcc (GCC) 8.5.0 20210514 (Red Hat 8.5.0-20), 64-bit

Paso 2: Creación de Roles y Gestión de Permisos

Creación de estructura de roles (admin, developer, read-only) con permisos granulares:

-- Conectar como superadmin (psql -U postgres)
psql -U postgres

-- Crear rol ADMIN con privileges elevados
CREATE ROLE admin WITH LOGIN PASSWORD 'admin123' CREATEDB CREATEROLE;

-- Crear rol DEVELOPER para desarrollo
CREATE ROLE developer WITH LOGIN PASSWORD 'dev456' NOCREATEDB;

-- Crear rol READ_ONLY para reportes (sin INSERT/UPDATE/DELETE)
CREATE ROLE read_only WITH LOGIN PASSWORD 'readonly789';
CREATE GROUP grupo_reportes;
ALTER GROUP grupo_reportes ADD USER read_only;

-- Verificar roles creados
\du
-- Role name | Attributes | Member of
-- admin     | Create role, Create DB | {}
-- developer | | {}
-- postgres  | Superuser, Create role, Create DB | {}
-- read_only | | {grupo_reportes}

-- Cambiar password de rol
ALTER ROLE developer WITH PASSWORD 'nuevaPass123';

-- Conceder permisos de administración
GRANT ALL ON DATABASE production TO admin;
GRANT CONNECT ON DATABASE production TO developer, read_only;

Paso 3: Configuración de Conexiones Remotas

Modificar configuración para permitir acceso desde máquinas remotas:

# En servidor CentOS:

# 1. Editar postgres.conf (parámetros servidor)
sudo vi /var/lib/pgsql/12/data/postgresql.conf
# Buscar y cambiar:
# listen_addresses = '*'      (escuchar en todas IPs, no solo localhost)
# port = 5432                 (puerto por defecto)
# max_connections = 100       (máximo conexiones simultáneas)
# shared_buffers = 256MB      (buffer memoria compartida)

# 2. Editar pg_hba.conf (autenticación)
sudo vi /var/lib/pgsql/12/data/pg_hba.conf
# Agregar línea (permite conexión usuario 'developer' desde cualquier IP con password):
host    all             developer       0.0.0.0/0               scram-sha-256

# Para admin solo desde redes confiables:
host    all             admin           192.168.1.0/24          scram-sha-256
host    all             admin           10.0.0.0/8              scram-sha-256

# 3. Recargar configuración (sin reiniciar)
sudo systemctl reload postgresql-12

# 4. Abrir puerto 5432 en firewall (si existe)
sudo firewall-cmd --permanent --add-port=5432/tcp
sudo firewall-cmd --reload

# 5. Verificar escucha en puerto 5432
sudo netstat -tuln | grep 5432
# tcp  0  0 0.0.0.0:5432  0.0.0.0:*  LISTEN
# tcp6 0  0 :::5432       :::*       LISTEN

Paso 4: Creación de Schema Relacional Avanzado

Diseño de base de datos con tipos avanzados de PostgreSQL (ENUM, JSON, herencia, índices):

-- Conectar como admin
psql -U admin -d production

-- 1. Crear tipo ENUM para estados
CREATE TYPE status_pedido AS ENUM ('pendiente', 'confirmado', 'enviado', 'entregado', 'cancelado');

-- 2. Tabla CLIENTES con validación
CREATE TABLE clientes (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    telefono VARCHAR(20),
    direccion_json JSONB DEFAULT '{}'::jsonb,  -- Dirección flexible (JSON)
    fecha_registro TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    activo BOOLEAN DEFAULT TRUE,
    CHECK (char_length(nombre) >= 3)  -- Al menos 3 caracteres
);

-- 3. Tabla PRODUCTOS con categoría
CREATE TABLE categorias (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE productos (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(150) NOT NULL,
    categoria_id INT NOT NULL REFERENCES categorias(id),
    precio NUMERIC(10, 2) NOT NULL CHECK (precio > 0),
    stock INT DEFAULT 0 CHECK (stock >= 0),
    metadata JSONB DEFAULT '{}'::jsonb  -- Atributos varaibles (color, talla, etc)
);

-- 4. Tabla PEDIDOS (con tipo ENUM)
CREATE TABLE pedidos (
    id SERIAL PRIMARY KEY,
    cliente_id INT NOT NULL REFERENCES clientes(id) ON DELETE RESTRICT,
    fecha TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    estado status_pedido DEFAULT 'pendiente',  -- Usa tipo ENUM
    total NUMERIC(12, 2) DEFAULT 0,
    notas TEXT
);

-- 5. Tabla LINEA_PEDIDO (relación N-N)
CREATE TABLE linea_pedido (
    id SERIAL PRIMARY KEY,
    pedido_id INT NOT NULL REFERENCES pedidos(id) ON DELETE CASCADE,
    producto_id INT NOT NULL REFERENCES productos(id) ON DELETE RESTRICT,
    cantidad INT NOT NULL CHECK (cantidad > 0),
    precio_unitario NUMERIC(10, 2) NOT NULL,
    subtotal NUMERIC(12, 2) GENERATED ALWAYS AS (cantidad * precio_unitario) STORED
);

-- 6. Crear índices para optimización
CREATE INDEX idx_clientes_email ON clientes(email);
CREATE INDEX idx_pedidos_cliente ON pedidos(cliente_id);
CREATE INDEX idx_pedidos_estado ON pedidos(estado);
CREATE INDEX idx_productos_categoria ON productos(categoria_id);
CREATE INDEX idx_linea_pedido_pedido ON linea_pedido(pedido_id);

-- 7. Verificar estructura
\dt
\d productos

-- QUERY 1: Window Function - Ranking de clientes por gasto
SELECT 
    c.nombre,
    SUM(p.total) as gasto_total,
    ROW_NUMBER() OVER (ORDER BY SUM(p.total) DESC) as ranking,
    RANK() OVER (ORDER BY SUM(p.total) DESC) as rank_con_empates
FROM clientes c
LEFT JOIN pedidos p ON c.id = p.cliente_id
GROUP BY c.id, c.nombre
ORDER BY ranking;

-- QUERY 2: Window Function - Comparar pedido actual vs próximo
SELECT 
    id,
    cliente_id,
    estado,
    total,
    LAG(total, 1, 0) OVER (PARTITION BY cliente_id ORDER BY fecha) as monto_anterior,
    LEAD(total, 1, 0) OVER (PARTITION BY cliente_id ORDER BY fecha) as monto_proximo,
    total - LAG(total, 1, 0) OVER (PARTITION BY cliente_id ORDER BY fecha) as diferencia
FROM pedidos
ORDER BY cliente_id, fecha;

-- QUERY 3: CTE (Common Table Expression) - Clientes con pedidos>$100
WITH clientes_gastadores AS (
    SELECT 
        c.id,
        c.nombre,
        SUM(p.total) as gasto
    FROM clientes c
    JOIN pedidos p ON c.id = p.cliente_id
    GROUP BY c.id, c.nombre
    HAVING SUM(p.total) > 100
)
SELECT * FROM clientes_gastadores
ORDER BY gasto DESC;

-- QUERY 4: JSON operators - Extraer ciudad del JSON
SELECT 
    nombre,
    email,
    direccion_json->>'ciudad' as ciudad,
    direccion_json->>'calle' as calle
FROM clientes
WHERE direccion_json->>'ciudad' = 'Madrid';

-- QUERY 5: Array aggregation - Todos productos en cada pedido
SELECT 
    p.id as pedido_id,
    c.nombre,
    p.total,
    STRING_AGG(pr.nombre || ' (x' || lp.cantidad || ')', ', ') as productos
FROM pedidos p
JOIN clientes c ON p.cliente_id = c.id
JOIN linea_pedido lp ON p.id = lp.pedido_id
JOIN productos pr ON lp.producto_id = pr.id
GROUP BY p.id, c.nombre, p.total;

Paso 6: Vistas y Vistas Materializadas

Creación de vistas para reportes reutilizables y optimización de queries frecuentes:

-- VISTA 1: Reporte de clientes con resumen de pedidos
CREATE VIEW v_reporte_clientes AS
SELECT 
    c.id,
    c.nombre,
    c.email,
    COUNT(p.id) as num_pedidos,
    SUM(p.total) as total_gastado,
    AVG(p.total) as ticket_promedio,
    MAX(p.fecha) as ultima_compra
FROM clientes c
LEFT JOIN pedidos p ON c.id = p.cliente_id
GROUP BY c.id, c.nombre, c.email;

-- Usar vista (query simple)
SELECT * FROM v_reporte_clientes WHERE total_gastado > 100;

-- VISTA 2: Productos bajo stock (alertas)
CREATE VIEW v_productos_bajo_stock AS
SELECT 
    id,
    nombre,
    categoria_id,
    stock,
    CASE 
        WHEN stock = 0 THEN 'CRÍTICO'
        WHEN stock < 5 THEN 'BAJO'
        ELSE 'OK'
    END as nivel_stock
FROM productos
WHERE stock < 10;

-- VISTA MATERIALIZADA: Reporte pesado (stats por categoría)
CREATE MATERIALIZED VIEW mv_stats_categorias AS
SELECT 
    cat.id,
    cat.nombre,
    COUNT(DISTINCT p.id) as num_productos,
    COUNT(DISTINCT lp.pedido_id) as pedidos_realizados,
    SUM(lp.cantidad) as unidades_vendidas,
    SUM(lp.subtotal) as ingresos,
    AVG(p.precio) as precio_promedio
FROM categorias cat
LEFT JOIN productos p ON cat.id = p.categoria_id
LEFT JOIN linea_pedido lp ON p.id = lp.producto_id
GROUP BY cat.id, cat.nombre;

-- La primera consulta es lenta (calcula en runtime)
SELECT * FROM mv_stats_categorias;  -- Rápido (datos precalculados)

-- Refrescar vista materializada cuando nuevos datos
REFRESH MATERIALIZED VIEW mv_stats_categorias;

-- Refrescar sin bloquear consultas (paralelo)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_stats_categorias;

-- Listar todas vistas
\dv
\dm  -- Listar vistas materializadas

❓ Preguntas Frecuentes

¿Cuáles son las diferencias principales PostgreSQL vs MySQL / MariaDB?

PostgreSQL: Tipos datos ricos (JSON, ARRAY, RANGE), Window Functions nativas, MVCC para mejor concurrencia, transacciones más robustas, extensiones (PostGIS), mejor para datos complejos. MySQL: Más rápido para queries simples, replicación más simple, menos recursos, mainstream en hosting compartido. Elección: PostgreSQL si: datos complejos, aplicación crítica, necesitas funciones avanzadas. MySQL si: startup rápida, datos simples, máximo compatibilidad hosting. Sintaxis: 90% compatible, pero diferencias: SERIAL vs AUTO_INCREMENT, plpgsql vs MySQL procedimientos, array indexing.

¿Qué es pg_hba.conf y por qué mi conexión remota no funciona?

pg_hba.conf: Archivo que controla AUTENTICACIÓN (quién se conecta y de dónde). Líneas: [tipo conexión] [base] [usuario] [origen IP] [método autenticación]. Problemas comunes: 1. Línea no existe en pg_hba.conf (agregar) 2. Protocolo correcto (host para TCP, local para socket Unix) 3. Método autenticación (trust/md5/scram-sha-256) 4. IP source filtrada (poner 0.0.0.0/0 para cualquier IP) 5. listen_addresses en postgresql.conf no configurado a '*'. Debug: Ver logs: tail -f /var/lib/pgsql/12/data/log/postgresql.log

¿Cómo conceder permisos correctamente a roles? ¿Qué diferencia hay entre usuario y grupo?

En PostgreSQL, no existe diferencia usuario vs grupo: TODO es ROLE. ROLEs con LOGIN = usuario que se conecta. ROLEs sin LOGIN = grupo (permisos reutilizables). Conceder permisos: GRANT [permisos] ON [objeto] TO [role]. Ejemplo: GRANT SELECT, INSERT ON tabla_usuarios TO developer. Herencia: ALTER GROUP grupo_reportes ADD USER maria; (Maria hereda permisos del grupo). GRANT SELECT ON ALL TABLES IN SCHEMA public TO grupo_reportes. Revoke: REVOKE INSERT ON tabla_usuarios FROM developer; (quitar permiso específico). Verificar: \du (listar roles), \dp (listar permisos tablas).

¿Qué son Window Functions y cómo son diferentes de GROUP BY?

GROUP BY: Colapsa filas (agrupa por valor). Resultado tiene tantas filas como grupos. No ves datos fila original (solo agregado). Window Functions: No colapsa. Cada fila original se mantiene PERO tienes contexto de grupo (ej: ranking, LAG anterior, promedio grupo). Ejemplo: GROUP BY estado da 5 filas (1 por estado). Window Function da todas filas originales (si 1000 pedidos) pero con ranking por estado en cada fila. Sintaxis: funcion() OVER (PARTITION BY estado ORDER BY fecha). PARTITION BY = GROUP BY equivalente, ORDER BY = orden dentro grupo. Funciones comunes: ROW_NUMBER(), RANK(), DENSE_RANK(), LAG(), LEAD(), SUM() OVER (...), AVG() OVER (...).

Mi vista MATERIALIZADA se ve "stale". ¿Cuándo refrescarla automáticamente?

Vistas Materializadas: Son snapshots (foto congelada de query). Datos no actualizan automáticamente. Opciones refresco: 1. Manual: REFRESH MATERIALIZED VIEW mv_nombre (ejecutar cuando sea necesario). 2. Programado: trigger que lanza refresh cada N minutos (cron + script psql). 3. Event scheduler (no nativo en PostgreSQL, requiere workaround con cron). Mejor práctica: Vistas materializadas para REPORTES (refrescar cada noche), NO para datos operacionales (usa vistas comunes, datos reales siempre). Performance: REFRESH MATERIALIZED VIEW CONCURRENTLY (no bloquea lecturas mientras refresca).

¿Cómo trabajar con JSON en PostgreSQL? ¿Cuándo usar JSON vs tabla relacional normal?

JSON en PostgreSQL: Almacenar datos semi-estructurados (flexible, no schema fijo). Tipos: JSON (texto, revalida cada vez), JSONB (binario, más rápido). Operadores: ->> (extrae valor como texto), -> (extrae como JSON), @> (contiene), ? (clave existe), @? (path query). Ejemplo: columna metadata '{"color": "rojo", "talla": "M"}'. Query: WHERE metadata->>'color' = 'rojo'. Cuándo usar JSON: Atributos variables (producto A tiene color, producto B tiene procesador). Cuándo NO: datos frecuentemente queryados (mejor columna relacional). Índices: CREATE INDEX idx_metadata ON tabla USING GIN (metadata); (permite búsqueda rápida en JSON).

¿Cómo monitorizar y optimizar performan ce de PostgreSQL?

Herramientas: psql meta-command \timing (medir duración query), EXPLAIN ANALYZE (ver plan ejecución + real runtime), pg_stat_statements extension (queries más lentas). Slow queries: Habilitarlos: log_statement = 'all', log_min_duration_statement = 1000 (registra queries >1seg). Índices: Ver índices no usados: SELECT * FROM pg_stat_user_indexes WHERE idx_scan = 0; (DROP si nunca usado). Ver índices grandes: SELECT schemaname, tablename, indexname, pg_size_pretty(pg_relation_size(indexrelid)) FROM pg_indexes WHERE schemaname='public'; Conexiones: SELECT * FROM pg_stat_activity; (conexiones activas, qué query ejecutan). SELECT datname, count(*) FROM pg_stat_activity GROUP BY datname; (conexiones por BD). Hot tables: SELECT schemaname, tablename, seq_scan, idx_scan FROM pg_stat_user_tables ORDER BY seq_scan DESC; (tablas con tabla scan frecuentes = falta índice).

📋 Conclusiones Técnicas

📚 Aprendizajes Principales

PostgreSQL es DBMS empresarial con features avanzadas (Window Functions, JSON, CTEs) que simplifica queries complejas. Administración es crítica: configurar pg_hba.conf correctamente, gestionar roles/permisos, monitorizar performance. Vistas (normales y materializadas) son herramientas poderosas para encapsular lógica y mejorar performance. Diferencias vs MySQL: PostgreSQL requiere más atención a configuración pero ofrece potencial sin límites para datos complejos.

⚠️ Desafíos Encontrados

1. Configuración pg_hba.conf confusa (orden de líneas importa, especificidad se cuenta). 2. Window Functions sintaxis compleja (OVER/PARTITION BY/ORDER BY requiere razonamiento nuevo). 3. Vistas materializadas "stale" (datos desactualizados requiere estrategia refresh). 4. Performance JSONB vs tabla relacional (benchmark necesario para diseño correcto). 5. Transacciones MVCC pueden causar confusión (REPEATABLE READ vs READ COMMITTED).

🎯 Mejoras Futuras

1. Replicación Streaming: Replica en tiempo real a servidor standby (alta disponibilidad). 2. Particionamiento: Tablas enormes partidas por rango/hash (mejor performance). 3. Extensiones: PostGIS (geoespacial), HyperLogLog (aproximación cardinales), Citus (distributed PostgreSQL). 4. Monitoreo avanzado: Prometheus + Grafana para métricas tiempo real. 5. Backup automatizado: WAL archiving + PITR (point-in-time recovery).

❓ Preguntas de Defensa Técnica Anticipadas:
P1: ¿Cómo debugguear si conexión remota no funciona?

R: Checklist: (1) Verificar firewall abierto: sudo netstat -tuln | grep 5432. (2) Revisar pg_hba.conf tiene entrada para usuario/IP. (3) Recargar: sudo systemctl reload postgresql-12. (4) Ver logs: tail -f /var/lib/pgsql/12/data/log/postgresql.log. (5) Probar localmente: psql -U usuario. (6) Probar remoto: psql -h 34.67.X.X -U usuario -d database.

P2: ¿Diferencia entre VIEW y MATERIALIZED VIEW?

R: VIEW: ejecuta query cada vez, datos siempre frescos pero potencialmente lento. MATERIALIZED VIEW: precalcula y almacena (rápido en lectura, pero datos pueden estar "stale"). Uso: VIEW para datos simples/pequeños, MATERIALIZED VIEW para reportes pesados/históricos.

P3: ¿Cómo la Window Function ROW_NUMBER es diferente de GROUP BY?

R: ROW_NUMBER() numera cada fila (1, 2, 3...) manteniendo todas filas originales. GROUP BY agrupa e retorna solo 1 fila por grupo. Ejemplo: si 100 pedidos, ROW_NUMBER da 100 filas (cada una numerada por cliente), GROUP BY da N filas (1 por cliente con SUM total).
