🎯 Objetivo

Comprender el modelo de datos relacional y aprender a diseñar, normalizar e implementar bases de datos eficientes usando SQL. Esta tarea cubre desde el diseño lógico en diagramas ER hasta la optimización con índices y garantías de integridad referencial.

💡 Conceptos Clave

Modelo Relacional

Fundamento de bases de datos modernas. Organiza datos en tablas (relaciones) con filas (tuplas) y columnas (atributos). Relaciones definidas mediante claves primarias y foráneas.
Modelo Relacional ↗

Normalización

Proceso de estructurar datos para minimizar redundancia y mejorar integridad. Formas normales: 1NF, 2NF, 3NF, BCNF. Elimina dependencias parciales y transitivas.
Normalización ↗

SQL (Structured Query Language)

Lenguaje estándar para gestionar bases de datos relacionales. DDL (CREATE, ALTER, DROP), DML (INSERT, UPDATE, DELETE), DQL (SELECT). CRUD operations fundamentales.
SQL DDL ↗

Transacciones ACID

Operaciones que garantizan consistencia de datos: Atomicidad, Consistencia, Aislamiento, Durabilidad. BEGIN, COMMIT, ROLLBACK. Previene corrupción de datos ante fallos.
Propiedades ACID ↗

Índices y Optimización

Estructuras (B-Tree, Hash) que mejoran velocidad de búsqueda. Tipos: Primary Key, Unique, Compound, Full-text. Balancean lectura rápida vs. overhead en escritura.
Índices MariaDB ↗

Integridad Referencial

Garantiza validez de relaciones entre tablas mediante Foreign Keys. Previene datos huérfanos. Opciones: CASCADE, SET NULL, RESTRICT. Esencial para consistencia.
Foreign Key ↗

Paso 1: Análisis y Diseño ER

Paso 2: Crear Tablas con Restricciones

Implementar DDL con Primary Keys, Foreign Keys, y validaciones.

CREATE TABLE Departamentos (
    id_dpto INT PRIMARY KEY AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL UNIQUE,
    presupuesto DECIMAL(12,2),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE Empleados (
    id_emp INT PRIMARY KEY AUTO_INCREMENT,
    nombre VARCHAR(100) NOT NULL,
    dpto_id INT NOT NULL,
    salario DECIMAL(10,2) CHECK(salario > 0),
    FOREIGN KEY (dpto_id) REFERENCES Departamentos(id_dpto)
        ON DELETE RESTRICT ON UPDATE CASCADE
);

Paso 3: Normalización (1NF - 3NF)

Verificar que cada tabla esté en 3NF: Sin atributos multi-valuados, sin dependencias parciales, sin dependencias transitivas.

-- 1NF: Eliminar grupos repetidos
-- 2NF: Quitar dependencias de clave compuesta
-- 3NF: Remover dependencias transitivas
-- Ejemplo: Separar dirección en tabla aparte
CREATE TABLE Direcciones (
    id_dir INT PRIMARY KEY,
    emp_id INT, calle VARCHAR(100),
    ciudad VARCHAR(50), estado VARCHAR(50),
    FOREIGN KEY (emp_id) REFERENCES Empleados(id_emp)
);

Paso 4: Crear Índices Estratégicos

Mejorar rendimiento en consultas frecuentes sin sacrificar escritura.

-- Índices simples
CREATE INDEX idx_dpto_nombre ON Departamentos(nombre);
CREATE INDEX idx_emp_dpto ON Empleados(dpto_id);

-- Índice compuesto para JOINs frecuentes
CREATE INDEX idx_emp_sal_dpto ON Empleados(dpto_id, salario);

-- UNIQUE index para garantizar unicidad
CREATE UNIQUE INDEX idx_emp_email ON Empleados(email);

Paso 5: Transacciones y Consistencia

Implementar transacciones multi-tabla para operaciones críticas.

START TRANSACTION;

UPDATE Departamentos SET presupuesto = presupuesto - 50000
WHERE id_dpto = 3;

INSERT INTO Empleados (nombre, dpto_id, salario)
VALUES ('Juan Pérez', 3, 50000);

-- Si falla algo, ROLLBACK automático
COMMIT;

Paso 6: Queries Avanzadas y Reportes

Crear vistas y consultas que aprovechen relaciones normalizadas.

-- Vista con JOINs y agregaciones
CREATE VIEW v_reporte_dptos AS
SELECT d.nombre, COUNT(e.id_emp) as empleados,
       AVG(e.salario) as salario_promedio,
       SUM(e.salario) as nómina_total
FROM Departamentos d
LEFT JOIN Empleados e ON d.id_dpto = e.dpto_id
GROUP BY d.id_dpto
ORDER BY nómina_total DESC;

❓ Preguntas Frecuentes (FAQ)

¿Cuál es la diferencia entre 1NF, 2NF y 3NF?

1NF (First Normal Form): Elimina atributos multi-valuados. Cada celda contiene un único valor.

2NF: Cumple 1NF + sin dependencias parciales. Todo atributo no-clave depende de la CLAVE COMPLETA.

3NF: Cumple 2NF + sin dependencias transitivas. Los atributos no-clave dependen solo de la clave primaria, no de otros atributos.

Ejemplo: Una tabla de "Empleado-Proyecto-Horas" debe separarse en Empleados, Proyectos, y Asignaciones(emp_id, proy_id, horas).

¿Cuándo usar índices? ¿Cuál es el costo?

Usar índices para: Columnas en WHERE, JOIN ON, ORDER BY frecuentes. Evitar en tablas pequeñas.

Costos: +Espacio en disco, +Tiempo en INSERT/UPDATE/DELETE (mantener índice), -Tiempo en SELECT.

Regla: Si 90% es lectura y 10% escritura, indexar ayuda. Si es 50-50, medir con EXPLAIN.

¿Qué es una Foreign Key y por qué usarla?

FK: Columna que referencia la clave primaria de otra tabla, creando relación 1:N.

Beneficios: Evita datos huérfanos, garantiza integridad referencial, el DBMS valida automáticamente.

Sintaxis: FOREIGN KEY (dpto_id) REFERENCES Departamentos(id_dpto)

Opciones: ON DELETE CASCADE (borra deptes), ON DELETE SET NULL (nulifica), ON DELETE RESTRICT (previene borrado).

¿Cómo optimizar una consulta lenta?

Pasos: 1) Usar EXPLAIN para ver plan de ejecución. 2) Verificar índices en WHERE/JOIN. 3) Evitar SELECT * (especificar columnas). 4) Usar JOINs en lugar de subconsultas cuando sea posible.

Ejemplo: Lento: SELECT * FROM Empleados WHERE YEAR(fecha_nac) = 1990 | Rápido: CREATE INDEX idx_fecha ON Empleados(fecha_nac)

¿Qué es una vista (VIEW) y cuándo usarla?

VIEW: Consulta guardada como tabla virtual. No almacena datos, recalcula al acceder.

Usos: Simplificar consultas complejas, ocultar estructura interna, reutilizar lógica, dar acceso limitado.

Limitaciones: Más lenta que tabla base, no UNIQUE en algunas bases de datos (MySQL permite UNIQUE VIEW).

¿Cómo manejar concurrencia y deadlocks?

Aislamiento (Isolation): Niveles: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE.

Deadlock: Dos transacciones esperan mutuamente. Solución: Ordenar acceso a recursos, usar timeouts, reducir duración de transacciones.

En MySQL: Usar LOCK IN SHARE MODE o FOR UPDATE, pero con cuidado.

¿Cuándo usar desnormalización (NoSQL, documentos)?

Normalización: Mejor integridad, menos almacenamiento, pero más JOINs.

Desnormalización: Menos JOINs, más rápido, pero redundancia de datos y riesgo de inconsistencia.

Decisión: Si necesitas velocidad de lectura crítica y actualizaciones infrecuentes (como cache), desnormalizar. Si integridad es crítica (finanzas), normalizar.

📋 Conclusiones y Reflexión

🎓 Aprendizajes

El modelo relacional es la base de casi todas las bases de datos empresariales. La normalización previene anomalías, pero requiere balance con rendimiento. SQL es profundo: desde DDL básico hasta optimización avanzada con índices y vistas.

⚡ Desafíos

Diseñar ER correctamente es más arte que ciencia. Balancear normalización vs. rendimiento requiere experiencia. Debugging de queries lentas frustrante. Entender planes de ejecución (EXPLAIN) es crucial.

🚀 Mejoras Futuras

Aprender sharding y particionamiento para big data. Explorar RDBMS específicos (PostgreSQL, Snowflake). Conectar con ORMs (Hibernate, SQLAlchemy) para abstracción. Implementar caché distribuido (Redis) para optimizar lecturas.

Preguntas Anticipadas - Defensa Oral:

Q1: "¿Por qué normalización si desnormalizar es más rápido?"
R: La normalización previene anomalías de inserción, actualización, borrado. Desnormalizar es último recurso cuando performance es crítica. En finanzas/salud, integridad > velocidad.

Q2: "¿Cómo hace MariaDB JOIN si hay múltiples índices?"
R: EXPLAIN muestra plan. Idealmente: índice en FK (lado muchos), PK en lado uno. Algunas veces nested loop, otras merge join. Depends en tamaño tabla.
Q3: "¿Cuándo usar VIEW vs. tabla?"
R: VIEW si es query reutilizada sin lógica pesada. Para agregaciones complejas frecuentes → tabla materializada. VIEW + índice en MariaDB es opción.
